SISTEMI DI SICUREZZA APPLICATI - PROGETTO GIUDMUNNA
===================================================

1) AUTENTICAZIONE E AUTORIZZAZIONE
----------------------------------
- Accesso alle pagine admin consentito solo a utenti autenticati.
- Verifica del ruolo admin prima di eseguire operazioni sensibili.
- Blocco accesso con uscita immediata se utente non autorizzato.


2) PROTEZIONE CSRF
------------------
- Token CSRF generato lato server con random_bytes.
- Token verificato con hash_equals su POST sensibili.
- Protezione applicata alle azioni critiche:
  - inserimento prodotto admin
  - modifica/rimozione/svuotamento carrello
  - conferma checkout


3) HARDENING SESSIONI
---------------------
- Cookie di sessione con:
  - httponly = true
  - samesite = Lax
  - secure = true quando il sito e in HTTPS
- session_regenerate_id(true) al login riuscito per mitigare session fixation.


4) PROTEZIONE SQL INJECTION
---------------------------
- Uso di query preparate (prepare + bind_param) per input utente.
- Cast esplicito dei campi numerici (es. id, quantita, prezzo).
- Vincoli DB coerenti (FK/UNIQUE) per integrita e riduzione stati anomali.


5) VALIDAZIONE INPUT SERVER-SIDE
--------------------------------
- Prezzo admin validato con:
  - limite lunghezza
  - formato decimale stretto (max 2 decimali)
  - no notazione scientifica
  - range consentito (> 0 e <= 999999.99)
  - arrotondamento deterministico a 2 decimali
- Quantita carrello limitata a range applicativo (1..99).
- Validazione parametri di redirect (next) con whitelist.


6) PROTEZIONE XSS (OUTPUT ENCODING)
-----------------------------------
- Escape HTML con htmlspecialchars(..., ENT_QUOTES, 'UTF-8') nei contenuti dinamici.
- Helper dedicati per output sicuro (es. h(), safe_image_src()).
- Riduzione del rischio XSS riflesso/persistente nella UI.


7) SICUREZZA REDIRECT E LINK
----------------------------
- Redirect post-login limitato a nomi pagina locali validi.
- Mitigazione open redirect tramite whitelist regex.
- Regola generale consigliata:
  - link interni: allowlist percorsi noti
  - link esterni: consentire solo http/https e validazione URL


8) SICUREZZA UPLOAD IMMAGINI
----------------------------
Flusso sicuro implementato nel pannello admin prodotti:
- Accesso consentito solo ad admin autenticato con CSRF valido.
- Verifica upload reale con is_uploaded_file.
- Limite dimensione file (max 5MB).
- Verifica MIME reale server-side con finfo_file.
- Solo MIME consentiti: image/jpeg, image/png, image/webp, image/gif.
- Verifica ulteriore contenuto immagine con getimagesize.
- Nome file univoco generato lato server con token casuale.
- Salvataggio in cartella uploads/ con path relativo nel DB.
- In alternativa, URL immagine valida solo se:
  - URL formalmente valida
  - schema http/https
  - estensione immagine consentita


9) HARDENING IMMAGINI IN OUTPUT
-------------------------------
- Controllo sicurezza src immagine:
  - blocco caratteri di controllo
  - allowlist path locale uploads/* con estensioni ammesse
  - allowlist URL assolute solo http/https con estensione immagine
- Se src non valida, immagine non renderizzata.


10) NOTE OPERATIVE IMPORTANTI
-----------------------------
- La validazione client-side migliora UX ma NON e sicurezza: autorita sempre server-side.
- Le query SQL vanno eseguite dal file .sql (schema/migrazioni), non a runtime nel codice app.
- In produzione evitare di mostrare dettagli tecnici di errore DB all'utente finale.


11) MIGLIORIE CONSIGLIATE (NEXT STEP)
-------------------------------------
- Centralizzare validazione input testuali (username, email, telefono, cap, citta).
- Applicare CSRF anche a eventuali altri form mutativi residui.
- Introdurre rate-limit/brute-force protection su login.
- Aggiungere Content-Security-Policy (CSP) e header di sicurezza HTTP aggiuntivi.
